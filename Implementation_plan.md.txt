# Master Implementation Plan

## Content-Provenance Watermarking for AI-Generated Media

### Project Objective

Build a web-based **AI-generated image provenance and verification system** that:

```text
AI Image Generation
        ↓
Image Preprocessing
        ↓
Invisible DWT-DCT Watermark
        ↓
SHA-256 Hash
        ↓
Provenance Registration
        ↓
PostgreSQL
        ↓
Image Distribution
        ↓
Verification
        ↓
Authenticity / Modification Result
```

The system will focus on **images for the MVP**. Video/audio, blockchain, C2PA interoperability, and neural watermarking remain future/advanced work, consistent with the report's scope. 

---

# 1. Project Understanding

## 1.1 What the system does

A user can:

1. Generate an AI image.
2. Protect the image using an invisible watermark.
3. Register its provenance in PostgreSQL.
4. Download/share the protected image.
5. Later upload the image for verification.
6. The system extracts the watermark.
7. The extracted ID is used to locate the provenance record.
8. SHA-256 is recalculated.
9. The system compares the submitted file with the registered file.
10. A verification result is returned.

The core idea is therefore:

> **Register first → embed provenance → verify later.**

It is **not** an AI-image detector or general deepfake detector.

## C. Image Preprocessing

Perform:

```text
Input Image
    ↓
Validate
    ↓
Decode
    ↓
RGB → YCbCr
    ↓
Use Y channel
    ↓
Normalize dimensions
```

### Important MVP decision

To make **resize robustness realistic**, the MVP will use a **canonical protected resolution**, preferably:

```text
512 × 512
```

If an input image has another aspect ratio, it will be resized/padded to the canonical size before watermarking.

For a later resized copy:

```text
512 × 512
      ↓
256 × 256
      ↓
Verification
      ↓
Normalize back to 512 × 512
      ↓
DWT-DCT extraction
```

This gives the DWT-DCT block grid a consistent reference.

**Cropping will be treated as an experimental robustness test, not a guaranteed MVP capability.**

# 6. Watermarking Design

This is the **most important technical component**.

The report specifically proposes DWT-DCT watermarking and expects the watermark to survive common transformations. 

## 6.1 Embedding Pipeline

```text
RGB Image
    ↓
YCbCr Conversion
    ↓
Y Channel
    ↓
Single-Level DWT
    ↓
HL/LH Subband
    ↓
8×8 Blocks
    ↓
DCT
    ↓
Coefficient Modification
    ↓
Inverse DCT
    ↓
Inverse DWT
    ↓
YCbCr → RGB
    ↓
Watermarked PNG
```

---

# 7. DWT Design

Use:

```text
Wavelet: Haar
Level: 1
```

DWT produces:

```text
             DWT
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
     LL      LH      HL      HH
```

### LL

Avoid embedding here.

It contains low-frequency image information and modifications are more noticeable.

### LH / HL

Use as the primary embedding region.

These provide the practical compromise between:

* imperceptibility
* robustness

### HH

Do not use as the primary watermark location because high-frequency information is more vulnerable to compression.

---

# 8. DCT Design

Divide the selected subband into:

```text
8 × 8 blocks
```

Apply:

```text
cv2.dct()
```

to every block.

Use **mid-frequency coefficients** rather than:

* DC coefficient
* extremely high-frequency coefficients

---

# 9. Watermark Payload

Do **not** put the entire provenance JSON inside the image.

Instead embed:

```text
MAGIC HEADER
+
PROVENANCE ID
+
CHECKSUM
```

Example:

```text
[32-bit magic]
[128-bit UUID]
[32-bit CRC/check value]
```

Total:

```text
192 bits
```

This payload is small enough to allow redundancy.

The complete information remains in PostgreSQL.

This follows the existing plan's core idea of using a short embedded identifier as a lookup key rather than storing a large provenance record inside the image. 

---

# 10. Error Correction

For MVP:

### Repetition coding

Repeat each payload bit multiple times.

Example:

```text
1 → 11111
0 → 00000
```

During extraction:

```text
11101 → majority = 1
```

This provides basic robustness against individual bit errors.

### Advanced version

Later:

* BCH
* Reed-Solomon

Do not implement these before the basic watermark works.

---

# 11. Embedding Strength

Use:

```text
delta
```

as the configurable embedding-strength parameter.

Conceptually:

```text
Higher delta
    ↓
More robust
    ↓
More image distortion
```

and:

```text
Lower delta
    ↓
Less distortion
    ↓
More fragile
```

Therefore:

**Do not hard-code a value such as `delta = 12` and call it optimal.**

Test several values:

```text
delta = 5
delta = 8
delta = 10
delta = 12
delta = 15
```

Then compare:

* PSNR
* SSIM
* extraction accuracy
* JPEG robustness
* visual quality

Choose the smallest value that provides acceptable robustness.

# 12. Blind Extraction

The verifier will **not have the original image**.

Therefore:

```text
Submitted Image
      ↓
Normalization
      ↓
DWT
      ↓
HL
      ↓
8×8 blocks
      ↓
DCT
      ↓
Coefficient comparison
      ↓
Payload bits
      ↓
Error correction
      ↓
CRC/magic validation
      ↓
Provenance ID
```

The magic header/checksum is important because it reduces the chance that an unrelated image produces a random sequence that looks like a valid watermark.

The system must never claim:

> "The watermark cannot be removed."

> **"The system is designed to maintain provenance information under common, non-adversarial transformations."**

A determined attacker may still destroy the watermark.

This is also consistent with the existing plan's explicit limitation.

# 16. SHA-256 Design

Use **two important hashes**.

### Hash 1 — Original

```text
AI Generated Image
       ↓
SHA-256
       ↓
original_hash
```

Useful for internal auditing.

### Hash 2 — Registered Watermarked Image

```text
Watermarked Image
       ↓
SHA-256
       ↓
registered_hash
```

This is the hash used for verification.

### Verification

```text
Uploaded Image
       ↓
SHA-256
       ↓
Compare with registered_hash
```

---

# 17. Important Difference

### Watermark

Answers:

> **Which registered provenance record does this image correspond to?**

### SHA-256

Answers:

> **Are these exact file bytes identical?**

Therefore:

```text
Watermark = persistent provenance link
SHA-256   = exact file integrity check
```

SHA-256 cannot itself prove authorship and will change after re-encoding, resizing, or compression. 

---

# 18. Verification Logic

The final system should have **four states**:

| Watermark       | Hash      | Result                    |
| --------------- | --------- | ------------------------- |
| Found           | Match     | `AUTHENTIC_UNMODIFIED`    |
| Found           | Different | `TRACED_BUT_MODIFIED`     |
| Not recoverable | —         | `WATERMARK_UNRECOVERABLE` |
| Not found       | —         | `NO_WATERMARK_FOUND`      |

### Meaning

#### Authentic

```text
Watermark ✓
Hash ✓
```

The uploaded file matches the registered watermarked file.

#### Traced but modified

```text
Watermark ✓
Hash ✗
```

The system can link it to a registered image, but the submitted file has changed.

#### Watermark unrecoverable

```text
Watermark ✗
```

The image may have undergone a transformation severe enough to destroy the watermark.

This is **inconclusive**, not proof of forgery.

#### No watermark

The image is not registered with this system.

This does **not** mean that the image is fake.

# 25. Watermark Evaluation

Measure:

### PSNR

Measures image distortion.

Higher:

```text
PSNR ↑
=
Less distortion
```

### SSIM

Measures structural similarity.

Closer to:

```text
1.0
```

means greater similarity.

### Extraction Accuracy

```text
Correctly recovered bits
─────────────────────────
Total embedded bits
```

### Robustness

Measure separately for each transformation.

For example:

```text
JPEG 90 → X%
JPEG 75 → X%
JPEG 50 → X%
Resize 50% → X%
Resize 75% → X%
```

Do not produce one generic "robustness = 95%" number.

### Processing Time

Measure:

```text
Embedding time
Extraction time
Hashing time
Verification time
```

The existing plan correctly emphasizes reporting measured results rather than fabricated performance/robustness values.

## The core contribution

The project can be summarized in one line:

> **An end-to-end provenance system that embeds a compact invisible identifier into AI-generated images using DWT-DCT watermarking, stores the associated provenance and integrity information in PostgreSQL, and verifies later copies by combining watermark extraction with SHA-256 comparison.**

That stays very close to the report's intended methodology while making the engineering implementation more realistic. 

### Final development priority

**Watermarking → Robustness → Backend → Database → AI Generation → Verification → Frontend → Deployment**

That is the order I would use for the actual project. The previous plan's own risk assessment also identifies the DWT-DCT embed/extract pipeline and blind extraction as the highest-risk components, so bringing that work to the front is the most important structural improvement.
